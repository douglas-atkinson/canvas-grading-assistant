# ARTIFACT_CONTRACTS.md

## Purpose

This is the Phase 4 ("Artifact Contract Inventory") deliverable called for by
`ROADMAP.md`. It documents, artifact by artifact, the data contracts already
produced and consumed by the Modules 1-8 prototype, using
`REPOSITORY_INVENTORY.md`'s Part 3 preview as the starting index.

**No production code, schema, configuration, or existing documentation was
moved, renamed, or edited to produce this document.** Every field below was
verified by reading the tracked source that produces or consumes it, on
`alpha-refactor` at commit `79e5b89`, unless explicitly marked otherwise (see
"How to Read This Document").

## How to Read This Document

Every claim in this document falls into one of three categories. Where the
category is not obvious from context, it is tagged inline:

- **(Fact)** - verified directly by reading the tracked producer/consumer code,
  a schema file, or a configuration file during this session. Unless tagged
  otherwise, treat every field value, filename, and behavior description below
  as a Fact.
- **(Inference)** - a conclusion drawn from combining two or more verified
  facts (for example, "these two independently-implemented functions must stay
  in agreement" is an inference from reading both functions).
- **(Recommendation)** - a proposal for the target architecture that does not
  exist in the prototype today. Every "Proposed target owner", "Recommended
  future model or contract name", and "Migration and backward-compatibility
  concerns" entry is a Recommendation unless it simply restates a placement
  `ARCHITECTURE.md` has already decided, in which case it is tagged **(Per
  ARCHITECTURE.md)**.

No field below was invented. Where a conventional envelope field (such as
`schema_version` or `artifact_type`) does not currently exist on an artifact,
this document says so explicitly rather than presenting it as present.

### Private-to-AI-Safe Boundary

The boundary is enforced by **three different mechanisms**, not one, found at
three different points:

1. `send_to_ai: false` boolean checks (Modules 3, 4, 8) - a declared-flag
   read.
2. Four required-`False` `contains_*` fields (Module 5.1's package manifest,
   re-checked by Module 6's `validate_ai_manifest`) - a declared-flags read,
   different shape from (1).
3. Recursive forbidden-key + explicit-flag scanning (`module_7/privacy.py`'s
   `assert_ai_safe`) - the only mechanism that does not simply trust a
   declared field, but actively searches the data structure itself.

**(Recommendation)** Phase 5's `PrivacyClassification`/`ArtifactMetadata`
model should unify these three into one type without weakening mechanism (3),
since it is the only one that would catch a privacy regression a producer
forgot to flag correctly.

### Identity-Restoration Boundary

Exactly one function in the entire tracked codebase performs identity
restoration: `module_8_create_grading_report.py`'s `restore_identity()`. It:

- requires the supplied manifest's `privacy.send_to_ai` to be exactly `False`;
- requires exactly one matching `anonymous_label` record;
- is the only place a PRIVATE artifact (the Module 3 manifest) is read again
  after Module 6 has already produced an AI-safe package from it indirectly;
- has an explicit, non-default escape hatch (`--allow-anonymous-report`) that
  skips restoration entirely and is loudly recorded in the resulting report's
  own `identity.identity_restored: false` and a `warnings` entry in Artifact 26.

No other module can restore identity; this is a hard, single-point boundary
by construction, matching `ARCHITECTURE.md`'s AD-010 exactly.

### Prompt-Marker and Regex-Recovery Coupling

The single most fragile coupling in the repository, now fully traced:

- **Producer:** `module_7/prompt_builder.py`'s `build_model_request()` writes
  the literal text `GRADING_PACKAGE_JSON\n<compact json>\n\nAI_SAFE_STUDENT_MATERIAL_JSON\n<compact json>`
  into `user_prompt`, with no named constant shared with any consumer (the
  marker strings are inline literals in this one function).
- **Consumer 1:** `module_7_revalidate.py`'s `extract_request_material()` -
  regexes `request_payload.json`'s `user_prompt` for those same two literal
  strings, used only as a **fallback** when `request_manifest.json`'s
  recorded file paths no longer resolve.
- **Consumer 2:** `module_8_create_grading_report.py`'s
  `extract_request_material()` - an **independently written function with
  the same name and the same regex pattern**, but used **unconditionally**
  (Module 8 never attempts a path-based recovery first, unlike Module 7's
  revalidator).
- **Risk:** any future change to `prompt_builder.py`'s marker text or
  separator (e.g., changing `\n\n` to `\n`, or renaming a marker) would
  silently break both consumers with no schema, type check, or test to catch
  it - confirmed by inspection that no test of any kind exists for this
  coupling today.

### Duplicated Validation Responsibilities

Three genuinely independent implementations of "is this a valid rubric /
result?" exist and were each traced to specific functions in this session:

1. `module_6_build_grading_package.py`'s `validate_rubric()` - validates
   `rubric.json` itself (criteria/items sum to declared maxima, unique IDs).
2. `module_7/validation.py`'s `rubric_maps()` + `validate_domain_rules()` -
   independently re-derives expected item/rule IDs from the same
   `grading_package["rubric"]` and validates the **model's response**
   against them (item ID membership, criterion/maximum agreement,
   status/score pairing, evidence-location resolution).
3. `module_8_create_grading_report.py`'s `rubric_contract()` +
   `normalize_items()` + `normalize_rules()` - independently re-derives the
   same expected structure a third time and re-validates the same
   grading-result invariants a second time (after Module 7 already did so),
   plus performs the authoritative score calculation.

None of these three share a function, a base class, or even a common
constant for the fixed tolerance used in float-sum comparisons (all three
independently use `1e-9` as a hardcoded literal - **(Fact)** the same
tolerance value chosen three times, not shared).

### Artifacts That Should Become Typed Models First

In priority order, agreeing with "Recommended Order for Formalizing Artifact
Contracts" below and with the Summary's "Recommended first contract to
formalize":

1. **`PrivacyClassification`/`ArtifactMetadata`** - three different
   enforcement mechanisms for the same underlying rule (see "Private-to-AI-
   Safe Boundary" above) exist today, and nearly every other artifact in this
   document must declare its own privacy status. Unifying these mechanisms
   without weakening the strictest one (`assert_ai_safe`'s recursive scan)
   comes first because every later contract - `Rubric`, `GradingRequest`,
   `ValidationReport`, `CourseRef` - is embedded inside artifacts that must
   already be able to declare their privacy classification honestly and
   consistently before their other fields are worth formalizing.
2. **`Rubric`/`RubricCriterion`/`RubricItem`** - remains the next
   highest-value domain contract: three independent implementations (Module
   6, Module 7, Module 8) currently re-derive and re-validate the same
   rubric shape, each hardcoding the same `1e-9` float tolerance separately;
   already `ROADMAP.md` Phase 5's own suggested first target.
3. **`GradingRequest`/saved-run material** - closing the prompt-marker regex
   coupling by carrying the grading package and student material as
   structured fields on the saved request, per `REPOSITORY_INVENTORY.md`
   Part 5's open question (this document recommends resolving it in Phase 5,
   agreeing with that open question's own suggested lean). Depends on #1 and
   #2 already existing.
4. **`ValidationReport`/`GradingResult`** - would let Module 7's and Module
   8's independent domain-validation logic be unified into one
   characterization-tested function, per the 2026-07-23 `ROADMAP.md`
   decision. Depends on #2.
5. **`CourseRef`/`AssignmentRef`/`AssignmentPackageRef`** - lower urgency (no
   safety-critical duplication, just inconsistent shapes and a conflated
   identifier space), but cheap to fix once `domain` exists.

### Recommended Order for Formalizing Artifact Contracts

**(Recommendation, synthesizing all of the above)**

1. `PrivacyClassification` / `ArtifactMetadata` (unifies three inconsistent
   mechanisms; touches nearly every artifact in this document; needed before
   any other model can declare its own privacy honestly).
2. `Rubric` / `RubricCriterion` / `RubricItem` (eliminates the three-way

## Accepted Phase 4 Decisions

These decisions were reviewed and accepted for this Phase 4 increment. They
record what to do, not how to implement it - no production code changes, no
domain-model-library choice, and no tests were made as part of accepting
them.

### a. First contract to formalize

`PrivacyClassification`/`ArtifactMetadata` is the first contract to
formalize, ahead of `Rubric`. See "Artifacts That Should Become Typed Models
First" and "Recommended Order for Formalizing Artifact Contracts" above for
the full rationale; both now agree with this decision and with the Summary's
"Recommended first contract to formalize."

### b. Privacy metadata must stay declarative, not a replacement for scanning

A future `PrivacyClassification`/`ArtifactMetadata` contract is a
**declarative** classification - it must not replace or weaken the recursive
structural scanning `assert_ai_safe()` already performs. The future design
must preserve defense in depth across all three layers found in this
inventory (see "Private-to-AI-Safe Boundary" above):

- a declared privacy classification (analogous to today's `send_to_ai`
  boolean);
- explicit content assertions such as `contains_*` fields;
- recursive, `assert_ai_safe`-style verification that does not simply trust
  a declared field but actively searches the data structure itself.

A typed model may unify how these three layers are _expressed_, but it must
not collapse them into a single trusted flag. The recursive scan remains the
layer that catches a producer that forgot to declare something correctly.

### c. Future transmission validation should scan both grading-package and student-material data

Today, `assert_ai_safe()` is only ever called on the AI-safe student material
(Artifact 8), not on the grading package (Artifact 9) - see Artifact 9's
privacy note and Unresolved Question 3 in the prior version of this document.
The accepted direction is that **future** transmission validation should
scan both:

- the AI-safe student material; and
- the grading package.

This is a decision about the target design, recorded for Phase 5+ planning.
**It is not a production-code change made in this task** - `module_7/privacy.py`
and every other tracked file remain exactly as they were before this
revision, and this decision should be implemented later behind a
characterization test proving it does not reject any currently-valid
grading package.

### d. Rename the colliding "validation report" concepts; keep old filenames loadable

This inventory found three artifacts that share "validation"/"report" naming
but mean different things (see "Missing or Conflicting Schema Versions" and
Artifact 14/20/26's notes). The accepted future conceptual names are:

- **`PackageBuildSummary`** for Module 6's always-successful
  `package_validation_report.json` (Artifact 14);
- **`ValidationReport`** for Module 7's genuine pass/fail
  `validation_report.json` (Artifact 20, and its revalidated form, Artifact 22) - the only one of the three that can actually be `false`;
- **`ReportSummary`** for Module 8's always-successful `report_validation.json`
  (Artifact 26).

This resolves Unresolved Question 2 from the prior version of this document.
Renaming is a future naming decision for the typed-model layer, not a
rename of the tracked prototype files today. **Historical filenames and
loaders must remain supported for saved prototype runs** - any future loader
for these three concepts must still recognize
`package_validation_report.json`, `validation_report.json`/
`validation_report.revalidated.json`, and `report_validation.json` by their
current names, since old runs will not be renamed retroactively.

### e. AI-safe submission manifest: preserve through parity, candidate for later deprecation

The AI-safe submission manifest (Artifact 4, `assignment_<id>[_<mode>]_ai_safe_manifest.json`)
has no downstream consumer anywhere in the tracked Modules 3-8 pipeline. This
resolves Unresolved Question 4 from the prior version of this document: the
manifest **must be preserved** through prototype parity (per `CLAUDE.md`'s
"do not delete prototype scripts/behavior prematurely" rule and
`ARCHITECTURE.md`'s AD-001), but it is recorded here as a **deprecation
candidate** for a later phase, once parity with the current prototype is
demonstrated and a maintainer decision is made about whether any planned
future consumer (e.g., a future review or audit surface) actually needs it.
No deprecation happens in this task.

### f. Saved provider-request artifacts should eventually carry structured fields; regex recovery stays as a compatibility loader

New saved provider-request artifacts should eventually carry the grading
package and student material as **structured fields** on the saved request
(see Artifact 16's recommendation and "Prompt-Marker and Regex-Recovery
Coupling" above), rather than only as text embedded between the
`GRADING_PACKAGE_JSON`/`AI_SAFE_STUDENT_MATERIAL_JSON` markers in the saved
prompt. The existing prompt-marker regex recovery
(`module_7_revalidate.py`'s and `module_8_create_grading_report.py`'s
independent `extract_request_material()` functions) **must remain available
as a backward-compatible loader** for historical runs that only have the
prompt-text form. The regex fallback should not be removed until
compatibility tests prove every historical saved run of interest can be
loaded through the new structured-field path instead - i.e., retiring the
regex fallback requires a test-backed migration, not just the new field's
existence.
